When does a Recursive Language Model beat RAG?

Three ways to read a huge text

RAG

Search the records, keep the 20 most relevant, answer from those. Two search engines: BM25 (exact words) and hybrid (words + meaning via embeddings).

Fast, cheap · blind to everything it didn't retrieve

Direct LLM

Paste the entire context into one prompt and ask. The simplest approach, and the one hit hardest by context rot: accuracy drops as the prompt grows.

Sees everything · expensive · max 1M tokens

>_

RLM

The context lives in a Python variable. The model writes code to explore it and, at depth 1+, calls a helper model on slices (e.g. "label these 300 reviews").

Reads everything in pieces · cost varies

T1 · Lookup"What did order X complain about?" One record matters.
T2 · Aggregation"What % of late orders blame delivery?" Every matching record matters.
T3 · Pairwise"List order pairs from the same city with opposite complaints." Pairs of records matter.

Inside an RLM run

Pick a run and step through what Claude wrote, what Python printed, and each helper call.

    What we learned

    Find one thing → RAG

    On lookups RAG-BM25 scores 0.90, as good as anything, at the lowest cost per question.

    Count or compare → RLM

    RAG scores ≤ 0.10 on aggregation and ≤ 0.07 on pairs. RLM depth 1: 0.60 and 0.84.

    Long context isn't enough

    Direct LLM sees every record yet scores 0.15 on aggregation and falls to 0 at 512K.

    Depth 1 is the sweet spot

    Depth 2 matched depth 1 (0.77 vs 0.76 on the same questions) at ~10× the cost and ~13× the time.

    Limitations. One model and one run per question; 6 questions per cell. The answer key is LLM-labeled and checked by a 200-review human audit (93.0% agreement). E-commerce last-mile delivery, not freight logistics.
